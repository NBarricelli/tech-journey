# **AZ-900 Notes**

## **Azure Compute Services**

### **Azure Virtual Machines**
- Virtual environments that can be deployed and managed quickly and easily for compute, storage, servers, etc.
- Virtualize an entire computer: OS and Hardware
- Great for applications requiring complete control of the environment
- Common use cases include testing & development, cloud app hosting, disaster recovery, and "lift and shift" migration.
- Grouped into families so you can choose a size based on workload needs.
  
  <img width="853" height="200" alt="image" src="https://github.com/user-attachments/assets/94891652-19f7-4875-bb70-b789e0aea395" />

When provisioning VMs, you choose the size (CPU cores, RAM), storage disks, and networking (IP addresses, port config, etc.). With Azure VMs, at a fundamental level, you start by selecting a family that matches your workload behavior. Then, you choose the size based on performance needs and scale as needed.

**Virtual Machine Scale Sets** allow you to create and manage groups of identical, load-balanced VMs. This ensures you do not have to manually keep VM config consistent and micromanage utilization. You specify the OS and quantity of VMs in the scale set, and Azure will scale them using **Auto-scale** when necessary to keep up with demand. These VMs are also deployed using Availability Sets for fault tolerance.

**Virtual Machine Availability Sets** improve VM resiliency within a region and reduce the chance that all VMs are affected by maintenance or disaster. Availability Sets group VMs by **Update Domain**, which are VMs that can be rebooted together during planned maintenance, and **Fault Domain**, which are VMs that share a potential power or network failure point.

<img width="573" height="381" alt="image" src="https://github.com/user-attachments/assets/73faf5d3-8506-450e-9ece-9b09f2786ead" />

Using the image above as an example: Each physical rack is also a Fault Domain because the resources hosted on that rack all share a power, network, or other physical failure point. Each VM, regardless of the Fault Domain or Physical Rack it is located in, is assigned to an Update Domain that it would share with another resource it can be updated/rebooted/etc with. All of this is located in one Availability Set.

### **Azure Virtual Desktop**
- A desktop and application virtualization service offered in Azure.
- Allows users to securely and remotely access Windows desktop environments and apps from many different device types and locations, with the primary requirement being internet connection.
- Reduces IT support overhead and can be easily distributed or revoked from specific user groups as needed.

### **Azure Containers**
- A lightweight virtual environment that contains its own OS and can be created, scaled out, and stopped dynamically.
- Virtualize the OS -- no hardware virtualization means faster deployments, snapshots, etc.
- Great for applications requiring portability and speed

### **Azure Functions**
- Event-driven, serverless compute option that executes based on triggers and therefore alleviating the need to keep resources provisioned when there are no events

### **Azure App Service**
PaaS service that can be used to create and host web apps in the cloud.

<img width="561" height="274" alt="image" src="https://github.com/user-attachments/assets/b087e960-358a-4ff0-94be-b9a6be644471" />

Each app service deployment has several front ends, which use a customized proxy-based routing module to send a request to a VM hosting the service being requested.\
These VMs run in an App Service Plan, which is a logical unit that helps with scaling web apps. All the VMs in an App Service Plan are identical and will run the same services.\
Azure Web App names have to be unique across all Azure Web Apps globally. This is because it becomes a DNS name (ex. *AzureWebApp01*.azurewebsites.net)

### **Azure Kubernetes Services**
A hybrid mix of PaaS and IaaS that can be used to run Kubernetes and Kubernetes clusters in the cloud. Similar to Azure App Service, you only pay for the compute resources in your cluster.

## **Azure Networking Services**

### **Azure Virtual Networking**
Virtual networks and subnets enable communication between Azure resources and users / on-prem computers. They provide capabilities like:
- Isolation and segmentation
- Traffic routing and filtering
- Connecting virtual networks, on prem resources, and Azure resources

**Virtual Network Peering** is when two Azure VNets are connected together. Traffic between the two VNets travels on Microsoft's private network, meaning the traffic is *not encrypted*. VNets can be peered in the same region or in different regions (global virtual network peering).

<img width="796" height="608" alt="image" src="https://github.com/user-attachments/assets/9dc835f2-a44a-4f59-a0fe-cd9167cf258d" />/

**Public endpoints** have a public IP address and are accessible anywhere in the world. **Private endpoints** only have a private IP address and only exist within a virtual network.

### **Azure DNS**
Azure DNS allows you to manage your DNS records in Azure. Internet-facing zones are called **public zones**, while zones used for Azure VNets are called **prviate zones**.

### **Azure VPN Gateway** 
Azure VPN Gateway is a service that provides secure connections between Azure Vnets and other networks. It uses a **gateway subnet**, inside of which are Microsoft-managed resources that implement and run the VPN Gateway.

There are three types of VPN Gateways:
| VPN Connection Type | Description |
| ---------------- | ----------- |
| **VNet-to-VNet** | Connects two Azure VNets together |
| **Site-to-Site** | Connects an Azure VNet to on-prem network |
| **Point-to-Site** | Connects a single device (phone, computer, etc) to an Azure VNet |

An important note about Azure VPN Gateway: VPN encryption isn't free. Encrypting, decrypting, and encapsulating traffic requires processing resources and adds network overhead.

### **Azure ExpressRoute**
Azure ExpressRoute, like Azure VPN Gateway, allows you to connect on-prem networks to Azure VNets; however, ExpressRoute offers significantly faster speeds over private connections. Instead of traffic flowing over the internet, traffic is flowing over a private connection via a Microsoft Enterprise Edge (MSEE) router. This private connection is called a **circuit**.


## **Azure Storage Services**

### **Azure Blob Storage**
Azure Blob Storage is designed for storing unstructured files like pictures, audio files, videos, documents, etc. These files are called **blobs**, and they are stored in containers, which can be thought of as a folder on a hard drive.

There are three types of blobs:
| Blob Type | Description | Example |
| --------- | ----------- | ------- |
| **Block blobs** | General purpose files optimized for storing large amounts of unstructured data | Pictures, videos, documents |
| **Append blobs** | Specialized for data that is continuously added to the end of a file | Log files |
| **Page blobs** | Optimized for frequent random read/write operations in virtual machines | Virtual Hard Disks (VHDs) |

### **Azure Disk Storage**
Azure Disk Storage provides persistent, block-level storage volumes used by Azure Virtual Machines (VMs). Azure managed disks are available in several types, including HDDs and SSDs, with different performance levels for different workloads.\
*Note: When creating an Azure VM, a managed OS disk is created and attached to the VM automatically.*

### **Azure Files**
Azure Files is a managed cloud file-sharing service that provides file shares accessible using standard protocols such as **Server Message Block (SMB)** and **Network File System (NFS)**. SMB file shares can be accessed using a standard UNC path, such as `\\server\share`.

Microsoft also offers **Azure File Sync**, which allows you to sync an on-prem Windows Server with an Azure file share, providing both local access and centralized cloud storage.

### **Storage Tiers**
Azure Storage is priced based on factors such as how much data you store and how frequently that data is accessed or modified. As such, Microsoft offers different storage tiers for different use cases.

| Tier Name | Use Case | Storage Cost | Access Cost | Note |
| --------- | -------- | ------------ | ----------- | ---- |
| **Hot** | Data accessed or modified frequently | Highest | Lowest | No minimum storage duration |
| **Cool** | Data accessed or modified infrequently | Lower | Higher | Recommended minimum storage duration of **30** days. Moving or deleting data earlier may result in an early deletion charge. |
| **Cold** | Data rarely accessed or modified but that still requires fast retrieval | Lower | Higher | Recommended minimum storage duration of **90** days. Moving or deleting data earlier may result in an early deletion charge. |
| **Archive** | Long-term storage for data that is rarely accessed | Lowest | Highest | Recommended minimum storage duration of **180** days. Archive is an offline tier, so data must be **rehydrated** to an online tier before it can be accessed. |
